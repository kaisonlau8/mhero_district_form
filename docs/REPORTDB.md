# 区域报表（reportdb）：系统计算「区域各指标情况一览」

目标：不再靠 `report_template.xlsx` 里约 4200 个公式出数，改为在 SQLite 里存数据、用 SQL + Python 计算，每张表一个独立网页。
**Excel 路径（`app/processor.py` + 模板 + `run_pipeline.py` 推送）原样保留，作为回退和对照。** reportdb 默认不参与生产流程。

  stores.py     门店表：模板种子 + 多维表格同步（只读）
  loaders.py    读源 xlsx / 历史日报 xlsx，复用 app/processor.py 的归一化函数

  tables.py     Block / Sheet 结构、0% / 0.0% 显示格式

## 1. 模板里每个指标的定义（从公式逆向）

模板 sheet：`直营店指标`、`区域指标排序`、`直营店指标排序`、`总表`、`常备件备库率` 为汇总页；`备件库存明细`、`招揽实施率`、`首保`、`二保`、`新保`、`续保` 为数据页（processor 把源报表写进去）。
数据页列字母（公式里的 `$B:$B` 等）与 `reportdb/datasets.py` 的列顺序一一对应。

### 1.1 数据页归一化（processor.py，reportdb 直接复用同一批函数）

| 数据集 | 规则 |
|---|---|
| 备件库存明细（stock） | M 列「实际可用」文本转数字（`parse_numeric_text`），非数字保留原文，SUMIFS 忽略 |
| 首保（first-service） | H「是否首保」重写：I「实际首保日期」有值 → `是`，否则 `否`（DMS 的 H 在超期/二次交付场景不可靠） |
| 续保（renewal） | 「续保投保率」12~13 列 + 「去年同期交付未新保车辆」（缺「保险到期时间」列，在 E/F 之间补空列）纵向合并；backlog 的门店列是**交付门店** |
| 其余 | 原样；空串视为空单元格 |

### 1.2 指标公式

记「区域」= 数据页 B 列，「门店」= D 列（门店名称），比较均**不分大小写、整串相等**（COUNTIF/SUMIFS 语义，不 trim）。

| 指标（块） | 数据页 | 应保/总数 | 实绩 | 比率 | 格式 |
|---|---|---|---|---|---|
| 首保实施率 | 首保 | COUNTIF(key) | COUNTIFS(key, H="是") | 实绩/应保 | 总表 0%，直营 0.0% |
| 二保实施率 | 二保（D=首保门店） | 同上，H「是否二保」="是" | | | |
| 新保投保率（新车交付量/新车投保） | 新保 | COUNTIF(key) | G「是否新保」="是" | | |
| 续保投保率（续保到期/实绩续保） | 续保 | COUNTIF(key) | H「是否续保」="是" | | |
| 招揽实施率（应招揽数/未招揽数） | 招揽实施率（保养提醒任务） | COUNTIF(key) | **未招揽数** = G「任务状态」="待处理" | (应招揽 − 未招揽)/应招揽 | |
| 常备件备库率 | 见 1.3 | | | | |

* 区域级（`总表`）：key = B 列，对 7 个区域（华北、华中 1、华南、西南、华东、西北、华中 2，固定顺序）各一行；`全国` = 各区域求和，比率 = 求和后的实绩/应保（不是各区域比率的平均）；除零 → `#DIV/0!`（reportdb 记为空，页面显示 `-`）；排名 `RANK(比率, 7 个区域)`（降序，并列同名次）。
* 门店级（`直营店指标`）：4 家直营店（南宁江南、天津北辰、郑州经开、001 武汉旗舰店），key = D 列；比率 `IFERROR(x/y, 0)`（除零记 0，**不是**空）；`合计` = 4 店求和。
* `区域指标排序` / `直营店指标排序`：`SORT(源块, 5, 1)`——**每个块**按块内第 5 列（排名）升序、稳定排序（并列保持原顺序，错误值排最后）。合计行 = `=总表!A10` 等直接引用，只引用前 4 列。

### 1.3 常备件备库率

* 行 = 经销商（113 家，模板 `常备件备库率` A:D 写死的 序号/编码/名称/区域），列 = 33 个备件号（F1:AL1，数字或 `55003001WC` 这类文本）。
* 格子 = `SUMIFS(备件库存明细!M:M, B:B = 经销商名称, C:C = 备件号)`：按**门店简称 = 经销商名称**、**备件号相等（数字样文本与数字等同、不分大小写）**对「实际可用」求和；无匹配为 0。第 3 行「标准备库量」、第 4 行分组标签（保养件/常用件）只是展示，**不参与计算**。
* 备库率 E = `COUNTIF(F:AK, ">0") / 32`：只统计 F:AK 共 **32** 列（第 33 列 AL「猛士817售后维修保护套件」会计算出库存但**不计入**分子分母——模板现状，reportdb 在 `spare_parts.counted=0` 里原样保留，如需纳入改该字段即可）。
* 区域级：应备店数 = 该区域经销商数（按 D 列「区域」，来自门店表）；实备店数 = 备库率 ≥ 80% 的店数；达标率 = 实备/应备；排名 = RANK(达标率)。
* 直营店级：备库率 = `IFERROR(INDEX(E, MATCH(门店名, C, 0)), 0)`（按名称取第一条）；是否达标 = 备库率 ≥ 0.8；达标率 = 1/0；合计行 = 备库率平均、`达标数/4`、`达标数/4`。

### 1.4 门店 → 区域 → 直营 的映射在哪里（重要发现）

* **经销商清单、区域、直营店名单、区域顺序、备件清单**都写死在模板里（`常备件备库率` A:D、`直营店指标` A3:A6、`总表` A3:A9、F1:AL4）。reportdb 把它们一次性搬进 DB 表（`stores`、`regions`、`spare_parts`，`reportdb/seed_data.json` 由模板生成），门店随后由多维表格「参与考核特约店清单」同步（`stores.py`，复用 `scripts/directory_sync.py` 的只读拉取）。
* **区域口径问题**：现行模板的 `总表` 用「数据页 B 列 = 区域名」做 COUNTIF，区域名是 `华北/华中 1/华南…`（公司区域，与多维表格「区域」一致），但 DMS 导出的「大区」列是 `北区/南区/中区/东区/华北区/西北区`。
  `processor.build_report` 并没有把 B 列映射成公司区域，所以**现在生产出的 Excel（如 `区域各指标情况一览1009.xlsx`）里区域级 6 个块全部是 0 / `#DIV/0!`**，`区域指标排序` 里还残留模板里的旧缓存数字。直营店层和常备件层不受影响。
* **正式口径（唯一的默认口径，`REPORTDB_REGION_MODE=store`）**：以多维表格「参与考核特约店清单」为**唯一权威**——
  * 明细行是否参与考核只认**门店编码 → 门店表**（找不到再按门店名称）；区域按该行的 **DMS 导出区域**（归一后）归属，DMS 为空记「无区域」并自动剔除，**不再回退多维表格区域**；
  * **门店不在多维表格（或已停用）的明细行，不计入任何指标**——区域、直营店、全国合计都不含（工厂自提虚拟店、罗伦士联名店等）。入库时每行打 `in_scope=0/1` 标记，不删数据，只是不计算；
  * 首页「被剔除的明细」与 `/api/quality` 会列出每个数据集被剔除的行数和门店，保证透明。
* 隐藏的诊断开关 `REPORTDB_REGION_MODE=source`（命令行 `--region-mode source`，页面不展示）：沿用 DMS「大区」文本、不剔除任何行，等同旧模板字面行为，只用来和现行 Excel 的区域表对数，**不要用于正式页面**。

### 门店同步（多维表格为准）

`python -m reportdb.ingest --sync-stores bitable --recompute --date …`（只读多维表格，只写 DB），或 `--sync-stores json`（读 `data/store_directory.json` 缓存，离线）。

* **权威同步默认开启**：多维表格里没有的门店置 `active=0`（停用，数据不删，回来后自动恢复）。要临时关闭设 `REPORTDB_STORES_AUTHORITATIVE=0`。
* **安全闸**：拉回的名单为空，或家数少于当前启用门店的 **50%**，整次同步中止（`StoreSyncAborted`），保留现有门店表，不改任何东西；命令行/钩子只打印警告，不影响后续入库。
* 门店变动后，**新入库的快照**自动按新门店表归属；历史快照保持当时的口径，如需按新门店表重算历史：`--recompute --remap --date …`。
2026-10-09 实测：多维表格实时返回 113 家，与模板 113 家完全一致。

### 1.5 常备件名单（可自定义，版本化）

* 默认 = 模板里的 33 个备件（v1，自 2000-01-01 起生效；「猛士817售后维修保护套件」`是否计入分母=否`，与模板一致：会统计库存但不进分子分母）。
* 管理员在 `/settings/spare-parts` 下载「当前名单」xlsx 模板（列：备件号、备件名称、是否计入分母、标准备库量、分组；已按现状预填）→ 修改后上传（.xlsx/.csv）→ **预览**（每个备件号是否匹配到库存、有货门店数、库存覆盖率、按新名单试算的达标店数与现名单对比）→ 选**生效日期**并确认 → 系统生成新版本并重算该日期之后的所有快照。
* 备件号匹配规则：去首尾/中间空格、横线、下划线，转大写；数字与数字样文本等同（Excel `SUMIFS` 的特性：`22806000` = `"22806000"`）。注意：这比旧模板略宽松（旧模板不去横线），当前 33 个备件号不含横线，对账结果不受影响。
* 历史：每次上传/回滚都新增一个版本，旧版本只读保留；**回滚** = 把旧版本复制为新版本并从指定日期起生效。任一快照按「生效日期 ≤ 快照日期 的最新版本」计算，所以改名单不会悄悄改变更早日期的数据（除非你选了更早的生效日期）。

## 2. 数据库（`REPORTDB_PATH`，默认 `data/reportdb/reportdb.sqlite3`，单文件 SQLite）

* 基础（schema v1）：`meta`（键值：同步时间、阈值等）、`regions`（区域及顺序）、`stores`（门店：编码/名称/区域/省市区/直营序号/启用/来源/`in_bitable`）、`spare_parts`（模板内置 33 个备件，仅作种子）、`snapshots`（每个快照日期的入库时间与各表行数）、`report_results`（每个快照×表×口径的计算结果 JSON）。
* 6 张明细表 `stock_items / task_items / first_service / second_service / new_policy / renewal`：主键 `(snapshot_date, row_no)`，列与模板列 A… 对齐；带区域的 5 张有 `region`、`in_scope`（renewal 另有 `origin`）。每个日期一份，历史累积，任意一天可重算；同一日期重复入库会整体替换。
* 迁移：`PRAGMA user_version` 递增，`python -m reportdb.migrate` 或任何入口启动时自动执行；首次建库从 `reportdb/seed_data.json`（由模板生成）种子化区域/门店/备件。

### 2.x 后续新增表

`stores.active/in_bitable`（权威同步）；5 张带区域的明细表新增 `in_scope`；`spare_lists` / `spare_list_items`（名单版本）、`spare_drafts`（上传预览草稿）；`users`、`sessions`、`audit_log`（登录）。schema v3 增加 `exemptions`、`exemption_log`、`user_stores`、`stores.supervisor`、`users.supervisor_name`（见第 7 节）。迁移由 `PRAGMA user_version` 自动执行（v1 → v2 对老库补列并把已有行按「有区域=计入」回填 `in_scope`）。备件号比较键 `part_key` 现为：去空格/横线/下划线、转大写、数字样文本规范成整数（见 1.5）。

## 3. 摄取

```

python -m reportdb.ingest --recompute --date 2026-10-09 [--remap]    # 只重算（--remap：按最新门店表重新归属区域）

```

### 每日自动入库（可选钩子，默认关闭；`MHERO_REPORT_ENGINE=reportdb` 时已隐含，见 7c）

`run_pipeline.py` 末尾有一段**默认关闭**的钩子。白话说明：

* **关闭（现状）**：每天 08:30 抓取 → 生成 Excel → 推送飞书，和以前完全一样，区域报表网页不会更新（网页里的数据停留在你手动入库的那一天）。
* **打开**（环境变量 `MHERO_REPORTDB=1`）：08:30 抓取完成、Excel 和飞书推送照常做完之后，**多做一步**：先读多维表格同步门店，再把当天 7 份表存进区域报表（按日期留存历史），并重算 5 张汇总表，网页随即显示当天数据。
* 这一步**失败只记录日志**（写入本次运行记录的 `reportdb` 字段），不会影响 Excel 生成和飞书推送；网页数据不变。
* 相关可选变量：`REPORTDB_SYNC_STORES=0`（入库前不同步门店，默认同步）、`REPORTDB_KEEP_DAYS=90`（只保留近 90 天快照，默认不清理）。

### 访问保护与登录（决定）

旧的 `scripts/web_console.py` 没有鉴权；reportdb 按用户要求做成**全站登录**，并取代之前的共享口令 `REPORTDB_TOKEN`（**已移除**，不再有任何口令参数/请求头）。

| 角色 / 权限 | 汇总表 | 明细（VIN/姓名） | 常备件名单设置 | 用户管理 |
|---|---|---|---|---|
| 查看者 viewer | ✔ | 脱敏（VIN 前3后4、姓名只留首字） | ✘ | ✘ |
| 督导 supervisor | ✔（全部区域） | **完整（默认）**，全部门店 | ✘ | ✘ |
| 查看者 + 「完整明细」 | ✔ | 完整 | ✘ | ✘ |
| 管理员 admin | ✔ | 完整 | ✔ | ✔ |

* 登录：用户名 + 密码（中文页面）；服务端会话（随机令牌，库里只存 SHA-256），cookie `reportdb_session`：HttpOnly、SameSite=Lax、HTTPS 下带 Secure（经 Cloudflare 时按 `X-Forwarded-Proto` 自动识别，也可 `REPORTDB_COOKIE_SECURE=1`），默认 12 小时过期（`REPORTDB_SESSION_HOURS`）。
* CSRF：所有 POST 表单带会话绑定的 CSRF 令牌（登录页用双提交 cookie），校验失败 403。`next` 跳转只允许站内路径。
* 防爆破：同一账号连续输错 5 次锁定 15 分钟（管理员可在用户管理页解锁）；同一 IP 5 分钟内失败 10 次直接 429。IP 取 `CF-Connecting-IP` / `X-Forwarded-For`（服务只监听 127.0.0.1，经 cloudflared 访问）。
* 密码：PBKDF2-HMAC-SHA256（60 万次迭代，随机盐，标准库实现、无额外依赖；`REPORTDB_PBKDF2_ITERS` 仅测试用），至少 10 位。改密码/重置密码/停用/改角色都会让该用户已有会话立即失效。所有登录、改权限操作写入 `audit_log`。
* **创建首个管理员**（CLI，不写死密码）：
  ```
  python -m reportdb.users create-admin --username admin          # 交互输入密码（不回显，输两次）
  REPORTDB_ADMIN_PASSWORD='…' python -m reportdb.users create-admin   # 非交互（部署脚本用）
  ```
  其他命令：`list`、`reset-password USER`、`disable USER`、`enable USER`。之后的用户在 `/admin/users` 里管理。
* **可插拔认证（为 Casdoor/OIDC 预留）**：`reportdb/auth/base.py` 定义 `AuthBackend` 接口（账号密码校验 / 外部登录跳转与回调 / 登出跳转）；会话、角色、CSRF、页面守卫与后端无关。`REPORTDB_AUTH_BACKEND=local`（默认）为本地账号；`=oidc` 切到 OIDC 授权码登录（`auth/oidc.py`：state + PKCE，用授权码换 access_token 后调 userinfo 取用户，首次登录自动建本地账号记录，角色按 `REPORTDB_OIDC_ADMIN_USERS` / `REPORTDB_OIDC_ADMIN_GROUPS` / `REPORTDB_OIDC_FULL_DETAIL_GROUPS` 映射，其余为查看者）。所需环境变量：`REPORTDB_OIDC_ISSUER`、`_CLIENT_ID`、`_CLIENT_SECRET`、`_REDIRECT_URI`（`https://<域名>/auth/oidc/callback`）、可选 `_SCOPES`、`_USERNAME_CLAIM`。切换后 `/admin/users` 变为只管角色/停用，密码在 IdP 管理。**OIDC 路径目前只用模拟 IdP 测过，接真实 Casdoor 时需要联调。**
* 部署建议：仍可在 Cloudflare Access 再加一层；公网暴露前务必已创建管理员并确认无默认账号（本系统没有任何默认账号）。

## 7. 分子的决定项与「豁免」申请流程

### 7.1 每个指标的分子是怎么定的（模板公式 = reportdb）

通用结构（`总表`/`直营店指标` 公式）：**分母** = `COUNTIF(明细!区域或门店列, 名称)`（该区域/门店的明细行数）；**分子** = `COUNTIFS(同一列, 名称, 决定列, 命中值)`。reportdb 里同样先剔除「门店不在门店表」的行（见 1.4），再按下表计算。

| 指标 | 明细表 | 决定分子的列 | 计入分子的值 | 分母过滤 | 决定列从哪来 |
|---|---|---|---|---|---|
| 招揽实施率 | 保养提醒任务 `招揽实施率`（`task_items`） | G「任务状态」`task_status` | **等于「待处理」**（模板如此，见下方提示） | 该区域/门店内全部任务行 | DMS 原值，不改写 |
| 首保实施率 | `首保`（`first_service`） | H「是否首保」`done` | 等于「是」 | 全部首保到期行 | **processor 重写**：I「实际首保日期」有值=是，否则=否（DMS 原 H 被覆盖） |
| 二保实施率 | `二保`（`second_service`） | H「是否二保」`done` | 等于「是」 | 全部二保到期行 | DMS 原值 |
| 新保投保率 | `新保`（`new_policy`） | G「是否新保」`done` | 等于「是」 | 全部新保行 | DMS 原值 |
| 续保投保率 | `续保`（`renewal`，含「去年同期交付未新保车辆」） | H「是否续保」`done` | 等于「是」 | 续保 + 未新保车辆全部行（`origin` 区分来源） | 续保原值；未新保车辆在 E/F 间补空列后并入，其「是否续保」同样取 H |

> ⚠ **请确认**：招揽实施率的分子在模板里是「任务状态 = 待处理」，字面上是「还没处理的任务」。reportdb 为保持与 Excel 完全一致照搬；如果业务上应当是「已完成」，需要改 `calc.py` 里 `task_status` 的命中值（一处），并同步改模板。豁免功能对该指标的含义是「按分子命中处理」，随命中值而定。

### 7.2 「修正结果」（原「豁免」）的含义（界面文案已写明）

* **只改分子，不改分母**：被批准的 VIN 在该指标上**视为分子命中**（首保=已首保、二保=已二保、新保=已新保、续保=已续保、招揽=已招揽实施），分母（该门店/区域的行数）不变。例：门店首保 2 台应保、0 台完成，豁免 1 台出口车 → 1/2。
* 不改源数据：明细里原来的「否」保持原样，页面在该行标「已豁免」。
* 以 **VIN + 指标** 为单位；同一 VIN 在该指标明细里的**所有行**一并计入（例如一台车有多条招揽任务）。
* **长期有效**：批准后之后每天的快照自动沿用，无需重复申请；批准时的「生效日期」默认为申请时看的快照日，管理员可改成更早（会重算这些历史快照）；「到期日期」默认空=永久，可选填。管理员可随时撤销，撤销后自动重算。
* 门店不在多维表格内的车辆**仍不计入**（申请时会被拒绝；即使库里有已批准记录也不计）。
* Excel 路径不变，豁免只在区域报表系统里生效；因此 Excel 日报与系统日报在有豁免时会不同。

### 7.3 角色与流程

| 角色 | 能做什么 |
|---|---|
| 督导 `supervisor` | 登录后看**全部区域的汇总表**和**全部明细行，VIN/姓名不脱敏**（督导默认带完整明细权限）；但**只能为自己负责门店的车辆提交申请**（申请页只列自己门店的车，后台再强校验）。在 `/exemptions/new`（申请修正结果）或 `/exclusions/new`（申请剔除）两个独立页面里找到自己范围内的车辆（**不支持批量粘贴 VIN**），在该车那一行填写理由并点该行的「提交申请」，一次只能提交一辆（后台拒绝批量）；`/exemptions/mine` 查看两类申请的状态、撤回待审批申请 |
| 管理员 `admin` | `/admin/exemptions` 待审批队列（按状态/指标/申请人/VIN/门店筛选）、批量批准/驳回、撤销已批准、查看每条的状态变更记录、导出 xlsx；也可自己申请（不受门店范围限制） |
| 查看者 `viewer` | 不能申请 |

* **督导范围**：门店表（多维表格「督导」列同步到 `stores.supervisor`）里督导姓名 = 该账号的「督导姓名」的启用门店，**并上**管理员在 `/admin/users/{id}/stores` 手工勾选的门店。督导只能为范围内的 VIN 申请（后台强校验，按行号/VIN 都一样）。
* 状态：`pending 待审批 → approved 已批准 / rejected 已驳回`；`approved → revoked 已撤销`；`pending → withdrawn 已撤回`。同一 VIN+指标同一时间只允许一条待审/生效记录。
* **审计**：表 `exemption_log` 记录每次状态变更（谁、何时、从什么状态到什么状态、意见），数据库触发器禁止修改和删除（只追加）；`audit_log` 另记用户与设置操作。
* **透明度**：明细行标「已豁免」；首页「已豁免」表和 `/api/quality.exemptions` 给出每个指标「因豁免而多计入分子的行数/VIN 数」。
* **管理员账号**：`python -m reportdb.users create-admin --username admin` 创建的 `admin` 就是管理员角色（拥有审批权和完整明细）。仓库和数据库里**不含**任何预置账号/密码，密码在 dfms 上设置。
* **SSO 账号同步**（`reportdb/auth/sso_sync.py`）：统一登录（Casdoor）里能进入本系统的账号会自动补进 `users` 表，不必等对方先登录：打开「用户管理」时自动同步（节流 60 秒）、后台每小时同步一次（`REPORTDB_SSO_SYNC_INTERVAL` 秒，0 关闭）、页面右上角「从 SSO 同步」立即同步。规则与登录相同（复用 `OidcBackend.map_identity`）：新账号身份取 Casdoor（管理员 / 督导），不分配门店；已有 oidc 账号只同步显示名 / 身份，Casdoor 停用则本地停用并踢下线（只停不启）；身份变化时明细权限按新身份重算并踢下线；只差大小写的账号不合并；本地账号（auth_source=local）不受影响；已无权限的账号不删除，只在同步结果里提示。需要 `MHERO_ADMIN_CRED_FILE` + `MHERO_ADMIN_API_BASE`（与身份同步共用）。
* **OIDC/Casdoor**：`REPORTDB_OIDC_SUPERVISOR_GROUPS`（或 `_SUPERVISOR_USERS`）把 Casdoor 角色/用户映射为督导，`ADMIN_*` 优先；督导的负责门店按其显示名匹配多维表格「督导」。
* 表：`exemptions`、`exemption_log`、`user_stores`，`stores.supervisor`、`users.supervisor_name`（schema v3，迁移自动执行）。

## 7b. 「剔除」：出口车分子分母都不计

### 7b.1 DMS 里「出口车」怎么标记（对 2026-10-09 真实数据的检查）

对 6 份明细的全部文本列搜索 出口/出国/海外/export：

| 数据集 | 列 | 命中 |
|---|---|---|
| 招揽实施率 | 门店名称 | `出口车专用` 24 行 |
| 首保实施率 | 门店名称 | `出口车专用` 1252 行 |
| 续保 | 门店名称 | `出口车专用` 485 行 |
| 二保 / 新保 | 门店名称 | 当日无 |
| 备件库存 | 门店名称 | `中国东风汽车工业进出口有限公司`（这是一家库存仓/公司，不是车辆标记，且库存表不参与分子分母） |
| 招揽 | 客户名/车主名 | 含「进出口公司」的客户（`进出口` 共 44 行，其中在门店表内仅 5～9 行）——**不可靠**，不能据此判定出口车 |

**结论：DMS 里可靠的标记是「门店名称 = 出口车专用」**（一个虚拟门店，无区域，不在多维表格门店表内）；没有车辆属性/销售类型/使用性质这类列。因此：

* 这些行**本来就因为「不在多维表格门店表」而不计入任何指标**；剔除规则把这件事显式化、可配置：即使以后有人把「出口车专用」加进多维表格，或有人切到诊断用的 `source` 口径，规则仍会把它们剔除。当前数据下规则**不改变任何数字**（实际剔除 0 行），首页/`/api/quality` 如实显示。
* DMS 没标成出口、而是「挂在真实门店名下」的出口车，没有可识别的列，只能靠督导**申请剔除**（下文）。

### 7b.2 规则表与页面

`exclusion_rules`（schema v4）：数据集 × 列 × 匹配方式（等于/包含，不分大小写）× 值 × 启用。出厂种子：5 个指标数据集的 `门店名称 = 出口车专用`（启用）+ 招揽 `车主名称 包含 进出口`（**默认关闭**的候选，仅供预览）。管理员在 `/settings/exclusion-rules` 看每条规则的命中行数、其中「计入范围内（实际剔除）」行数、主要门店；**新增前必须先预览**，确认后添加；添加/启用/停用/删除后**自动重算全部快照**，并写入操作审计。

### 7b.3 督导「申请剔除」（整车，不分指标）

见 7c：剔除现在是**整辆车**的申请（`exemptions.kind='exclude'`，`indicator='all'`），批准后这辆车在所有指标里都不计；与「修正结果」是两类独立申请，不能合并提交。被剔除的行在明细页标「已剔除」；首页「已剔除 / 已修正」表和 `/api/quality` 的 `exclusions`、`exclusion_rules` 给出每个指标「规则命中行数」「整车剔除申请的行/VIN 数」。门店不在多维表格的行仍整体不计。Excel 路径不受剔除/修正结果影响。

### 7c. 申请分两类：修正结果 与 剔除（2026-10-10 起）

| | 1. 修正结果（原「豁免」） | 2. 剔除 |
|---|---|---|
| 入口 | `/exemptions/new`（导航「督导申请 → 申请修正结果」） | `/exclusions/new`（导航「督导申请 → 申请剔除」） |
| 对象 | 某指标 × 某辆车（VIN） | **整辆车（VIN），不分指标**（库里 `indicator='all'`） |
| 效果 | 该指标上把「否」改成「是」：分子 +1，分母不变；只对该指标有效 | 该车**永久**标记为已剔除：所有指标（招揽/首保/二保/新保/续保）的分子分母都不计，首页、各区域/直营店/汇总表、日报、导出全部生效 |
| 列表 | 选指标，只列该指标当前结果为「否」的车；列与 `/data/*` 明细页一致 + 「已有申请」 + 必填理由 + 每行「提交申请」；已完成（结果为「是」）的车不会出现，硬提交也会被跳过（「结果已是『是』，无需修正」） | 所有指标明细里范围内、尚未被剔除的车辆合并按 VIN 去重（列：VIN、门店编码/名称、归属区域、涉及指标、已有申请）+ 必填理由 + 每行「提交申请」；已完成的车也可以剔除 |
| 待审批 | 不生效 | **不生效**（只有管理员批准后才生效；撤回/驳回都不会生效） |
| 生效后 | 跨快照持续；可设到期日期；撤销后恢复 | 永久（批准时忽略到期日期），**只有管理员「撤销」才恢复**；批准即重算自生效日期起的全部快照 |
| 重复 | 同 VIN × 同指标只能有一条待审批/已生效申请 | **同 VIN 只能有一条**待审批/已生效申请（不分指标） |
| 优先级 | | 高于修正结果：同一辆车既被修正又被剔除，则完全不计 |

* 两类**分开申请、分开审批**：申请页、导航、「我的申请」（`/exemptions/mine`，类型列「修正结果」/「剔除」，类型/指标/区域/门店筛选）、管理员审批页（`/admin/exemptions`，`?kind=exempt` 只看修正结果，`?kind=exclude` 只看剔除；导航「修正结果 / 剔除审批」）都带类型标签；每个申请页底部有对应类型的「我的申请明细」。`/data/*` 明细页保持只读，只给出两个申请页的链接。
* 已被剔除的车不再出现在两个申请页，也不能再提交修正结果。仍不支持批量粘贴 VIN，也没有证据说明输入框。
* 剔除后的数值口径：引擎里 `exclusions.excluded_expr` 的 VIN 条件不再带指标，所有 `calc._agg`、行标记、质量统计、日报都走同一个条件。
* **数据迁移（schema v5，随 `PRAGMA user_version` 自动执行，幂等）**：迁移前先把整个库备份为 `<库文件>.pre-v5.bak`；已有 `kind='exempt'` 的记录原样保留（即修正结果）；已有按指标的 `kind='exclude'` 记录全部改成 `indicator='all'`，同一 VIN 的多条待审批/已批准申请合并为一条（有已批准的留最早的已批准并取最早生效日期，其余已批准置「已撤销」、待审批置「已撤回」，都写 `exemption_log`，操作者 `migration`）；已批准的剔除到期日期清空（永久）；如有已批准的剔除，会自动重算全部快照，因为原来只在某一个指标上剔除的车现在所有指标都不计。


## 7c. 取消 Excel 日报：系统统一计算并导出

**报表引擎开关 `MHERO_REPORT_ENGINE`**：`excel`（默认，旧路径，不设就是它）｜`reportdb`（新）。

`reportdb` 引擎下，`run_pipeline.py` 的流程是：抓取 DMS（不变）→ 同步多维表格门店 → 7 份表入库（**入库是隐含步骤**，不需要再设 `MHERO_REPORTDB`）→ 计算 → 导出 `output/区域各指标情况一览MMDD.xlsx`（同日重复生成加 `_HHMMSS`，与旧规则一致）→ 飞书通知：卡片与旧路径同一个函数生成（标题、字段、「下载报表」按钮都不变；飞书卡片本身只有状态/文件名，没有指标数字），群里和全国收件人私聊附带的文件换成系统导出的这份。入库失败时本次状态为 `error`（日报是这条路径的产出，不会静默用旧数据）；单独的门店同步失败只记录并沿用现有门店表。

**日报文件**：`reportdb/daily_report.py`。5 张汇总表（直营店指标、区域指标排序、直营店指标排序、总表、常备件备库率）的版式沿用旧日报——样式骨架 `reportdb/assets/daily_report_style.xlsx` 是旧模板去掉明细页和全部内容后的样子（列宽、颜色、边框、合并单元格、条件格式），值是系统算出的数字（**无公式**，不依赖 Excel 重算）。口径是系统口径：门店以多维表格为准、已含豁免、已剔除。可选附明细 sheet（`/export/daily-report.xlsx?detail=1`，按下载者权限脱敏；流水线里用 `REPORTDB_DAILY_DETAIL=1`，但流水线文件会推给全国收件人，所以明细 sheet **固定脱敏**）。网页：`/reports/daily` 选日期/历史列表下载，`/export/daily-report.xlsx?date=YYYY-MM-DD` 任意一天重新导出。

**下线 Excel 管理（引擎=reportdb 时）**：
* `scripts/web_console.py`（:9003）：隐藏「默认模板」卡片，`/api/template`（查看/下载/上传）返回 410；爬取、生成、推送开关保留（生成走新引擎）。

## 8. 风险与已知差异

* 区域口径见 1.4：正式口径修复了现行 Excel 区域表为 0 的问题，数字会与现行 Excel 的区域表**不一致**（现行是 0）；直营店表、常备件表一致（直营店都在多维表格内）。
* 门店不在多维表格的明细行不计入任何指标（含全国）；想把它们算上，必须先在多维表格补门店。
* 多维表格误删/误改门店会直接改变口径（安全闸只拦「名单为空或少于一半」）；首页「被剔除的明细」可以发现异常。
* 备件号匹配比旧模板略宽松（去横线/空格/下划线），见 1.5。
* 浮点：个别比率与参照相差 ≤ 6e-17（求和顺序，1 ulp），显示值（0% / 0.0%）无差别。
* 排名遇到并列/空值的规则与 Excel 一致，但空值（除零）参与 `RANK` 时 Excel 会整列报错，reportdb 是让空值不参与排名。
* DMS 数据导出若改了列顺序，需同步改 `datasets.py`（和模板、processor 同样脆弱）。

## 7d. 逐条提交（2026-10-11，取代「勾选 + 底部统一提交」）

* **不允许批量提交**：`/exemptions/new`（修正结果）、`/exclusions/new`（剔除）没有「是否申请」勾选框、没有底部统一提交按钮。每一行有自己的小表单：桌面端最右一列「操作 → 提交申请」；手机卡片里是整行宽（≥44px）的「提交申请」。只提交这一辆车，该行自己的理由（必填，浏览器端先校验，后台再校验）。
* **后台强制**：`POST /exemptions/request`（字段 `reason_<行号>`）、`POST /exclusions/request`（字段 `xreason_<VIN>`）一次请求带多于 1 辆车（多个 reason/pick 字段、多个 `row_nos`/`vins`）整体拒绝并提示「每次只能提交 1 辆车的申请，不支持批量提交」，一条都不建；`exemptions.request_exemptions` / `request_exclusions` 也限制 `MAX_PER_REQUEST = 1`，脚本同样受限。理由为空、重复申请、结果已是「是」、不在督导门店范围、被剔除、CSRF、审计（`exemption_log`）规则不变。
* **提交后**：回到原申请页，保留指标/区域/门店/搜索/日期筛选，页顶显示结果，并在该车那一行下方显示行内成功/失败提示（`?row=…&ok=1#r-…`），「已有申请」列同步显示状态。成功后再提交同一辆会被「已有待审批」拒绝。
* 「我的申请明细」、筛选、区域、已有申请状态列保持不变。
